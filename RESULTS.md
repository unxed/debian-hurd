# Результаты PoC futex/signal на GNU Hurd

См. `PLAN.md` для контекста и целей.

## Как воспроизвести

`.github/workflows/run-hurd-poc.yml` (workflow_dispatch): собирает образ из
`hurd-image-parts/`, монтирует ext2-раздел через loop-device (rw), кладёт
`poc/*.c` в `/root/poc`, патчит `grub.cfg` (serial-консоль + убирает
`--readonly` у `ext2fs.static`), затем поднимает образ в QEMU
(`-nographic`-эквивалент, `-serial stdio`, TCG без KVM) и через
`.github/scripts/run_poc.py` (pexpect) логинится root'ом (пароль пустой),
собирает `poc/Makefile` и прогоняет оба бинарника. Полная стенограмма serial-
консоли сохраняется как артефакт `hurd-poc-transcript`.

Итоговый успешный прогон (все 4 PoC): https://github.com/unxed/debian-hurd/actions/runs/35338417571

## futex-подобная синхронизация: gsync_wait/gsync_wake

GNU Mach **не** реализует OSF/XNU-style `semaphore_create/wait/signal`
(отсутствуют в заголовках — `mach.h` их не декларирует). Вместо этого в
`<mach/gnumach.h>` есть нативный примитив, семантически идентичный Linux
futex:

```c
kern_return_t gsync_wait(task_t task, vm_address_t addr,
                          unsigned val1, unsigned val2,
                          natural_t msec, int flags);
kern_return_t gsync_wake(task_t task, vm_address_t addr,
                          unsigned val, int flags);
kern_return_t gsync_requeue(task_t task, vm_address_t src_addr,
                             vm_address_t dst_addr,
                             boolean_t wake_one, int flags);
```

`gsync_wait` атомарно проверяет, что 32-битное слово по `addr` равно `val1`;
если нет — возвращается немедленно (не `KERN_SUCCESS`), если да — блокируется
до `gsync_wake` по тому же адресу. Ровно `FUTEX_WAIT`/`FUTEX_WAKE`. Флаги:
`GSYNC_SHARED` (адрес общий между задачами, а не task-local),
`GSYNC_BROADCAST`, `GSYNC_MUTATE`, `GSYNC_QUAD`, `GSYNC_TIMED` — но сами
числовые значения этих макросов не установлены пакетом `hurd-dev` в этом
образе (объявлены только в комментариях `.defs`); для task-local
wait/wake они и не нужны (`flags=0`).

**Результат** (`poc/futex_poc.c`, generation-counter паттерн, 2000 итераций
wait→wake между двумя pthread-потоками одного процесса):

```
RESULT: OK iters=2000 blocked=2000 immediate=0 avg_us=158.39 min_us=55.78 max_us=9866.54
```

Ни одного потерянного пробуждения. Средняя задержка ~158 мкс (макс. ~9.9 мс —
похоже на джиттер QEMU TCG без KVM, а не свойство примитива). **Вывод:
futex-подобный примитив на голом Hurd есть и работает.**

## Асинхронная доставка сигналов: SIGUSR1 без SA_RESTART

`poc/sig_poc.c`: отдельный поток раз в 2 мс шлёт `SIGUSR1` через `kill()`,
основной поток 500 раз вызывает `nanosleep(50ms)` без `SA_RESTART` в
обработчике.

```
RESULT: handler_fired=500 eintr_in_nanosleep=0 full_sleep=500 matched_pairs=500 avg_us=611.43 min_us=353.40 max_us=33522.84
```

- Обработчик отработал **все 500/500** раз — доставка сигналов надёжна.
- Средняя задержка доставки ~611 мкс (хвост до 33 мс — вероятно опять
  TCG-эмуляция single-core, `-smp 1`).
- **Но `eintr_in_nanosleep=0`**: ни один `nanosleep()` не был прерван сигналом
  досрочно, хотя `SA_RESTART` не установлен. Обработчик вызывается «поверх»
  спящего потока, но сам блокирующий syscall не возвращает `EINTR` и не
  прерывается.

**Вывод:** доставка сигналов в обработчик работает и достаточно быстрая, но
Hurd, похоже, не прерывает блокирующие syscall'ы сигналом так, как это делает
Linux/BSD (`EINTR`). Изначально было неясно, это особенность `nanosleep` или
системное свойство — перепроверено ниже на `read()`.

## Перепроверка нюанса: EINTR на блокирующем read() (poc/io_poc.c)

20 итераций: пустой pipe, `read()` без данных (блокирует), через ~20мс поток
шлёт `SIGUSR1` без `SA_RESTART`, через ~150мс watchdog-поток пишет байт в pipe
как страховка на случай, если сигнал не прервёт `read()`.

```
RESULT: read_eintr=0 read_completed_via_watchdog=20 other=0 iters=20
```

**0 из 20** `read()` были прерваны сигналом — все 20 отработали только когда
watchdog записал байт в pipe, т.е. `read()` действительно ждал реальные данные,
а не был прерван по сигналу. Это тот же результат, что и с `nanosleep`, но уже
на настоящей блокирующей I/O-операции (RPC к `pflocal`-серверу, а не просто
таймер ядра). **Нюанс подтверждён и это системное свойство Hurd, а не
особенность конкретного вызова**: сигналы вызывают обработчик, но не приводят
к `EINTR` у блокирующих syscall'ов.

## Проверка sigaltstack + SA_SIGINFO + si_addr на SIGSEGV (poc/segv_poc.c)

Это отдельный примитив, критичный для рантайма Go: рост стека горутины по
guard-page и превращение разыменования nil-указателя в обычную Go-панику
требуют (1) обработчика, который выполняется на альтернативном стеке даже
если стек упавшего потока исчерпан, и (2) точного адреса аварии в
`siginfo_t.si_addr`. Тест: `mmap(PROT_NONE)` страница, преднамеренная запись
в неё, обработчик на `sigaltstack`.

```
RESULT: got_signal=1 ran_on_altstack=1 si_addr_match=1 expected=0x101053000 got=0x101053000
```

Всё сработало: сигнал доставлен, обработчик реально выполнился на
альтернативном стеке, адрес аварии совпал с ожидаемым **точно**. Это самый
важный положительный результат для варианта (а) — именно этот примитив, а не
futex или обычные сигналы, является наиболее фундаментальной зависимостью
рантайма Go от ОС.

## Итог по PoC (обновлён)

| Примитив | Нужен для | Результат |
|---|---|---|
| `gsync_wait`/`gsync_wake` (futex-аналог) | блокировки/мьютексы/каналы в рантайме | ✅ работает, ~130-160 мкс |
| Доставка сигнала в обработчик | `SIGURG`-preemption, вообще любая сигнальная логика | ✅ работает, ~300-600 мкс |
| `EINTR` на блокирующем syscall без `SA_RESTART` | ожидалось для классической Unix-модели прерывания I/O сигналом | ❌ не работает (ни `nanosleep`, ни `read`) — сигнал вызывает обработчик, но не прерывает вызов |
| `sigaltstack`+`SA_SIGINFO`+`si_addr` на SIGSEGV | рост стека горутины, nil-deref → panic | ✅ работает, адрес аварии точный |

Фундаментального блокера ни для (а), ни для (б) в примитивах синхронизации и
сигналов не нашлось. Единственный реальный минус — отсутствие `EINTR` у
блокирующих syscall'ов — не критичен для модели преемпции Go (`SIGURG`
асинхронно прерывает выполняющуюся в цикле горутину через переписывание PC в
обработчике, а не через `EINTR`; горутины, зависшие в syscall, Go и так
обрабатывает отдельным механизмом — подменой M, а не сигналом), но был бы
отдельной статьёй расходов для варианта (б), если бы транслятор Linux-ABI
полагался на нативное поведение Hurd вместо собственной эмуляции.

## Дополнительное исследование: сравнительная сложность (а) native Go port vs (б) Linux-транслятор

Помимо PoC, был проведён поиск по реальному опыту (issue-трекеры, документация
Hurd, исходники glibc/gccgo). Ключевые факты:

**1. Существующие попытки портирования Go на Hurd.** Нативного порта рантайма
Go (`gc`-тулчейн, тот, что используется на Linux/Darwin/Windows) на
`GOOS=hurd` никто не делал и не пытался — ноль прецедентов. Всё, что есть —
это `gccgo` (GCC-фронтенд для Go, другая модель рантайма поверх `libgo` и
`setcontext`-корутин): патчи Svante Signell 2018 года
(gcc-patches, ветка `tschwinge/t/hurd/go`), и открытая задача в трекере Hurd
(`gnu.org/software/hurd/open_issues/gccgo.html`), где явно обсуждается риск
порчи TLS вызовом `setcontext` на Hurd — то есть уже известная проблема
именно для модели gccgo/libgo, не имеющая отношения к нашим PoC (`gc`-рантайм
не использует `setcontext` для горутин, у него свой ассемблерный
switch-стек). `GOOS=hurd` в Go 1.12 зарезервирован именно "for use with
gccgo". Debian ни разу не собирал `golang-go` (нативный тулчейн) для Hurd.

**2. У Hurd нет плоской таблицы syscall номеров.** Это задокументированный
факт архитектуры (`gnu.org/software/hurd/hurd/rpc.html`): единственный
настоящий "системный вызов" в Mach — это `mach_msg` (IPC). Всё остальное
(`open`, `read`, `fork`, ...) — функции glibc, которые *внутри себя* делают
Mach RPC к серверам-трансляторам. Это принципиально отличается от Linux, где
Go-рантайм на ассемблере делает голый `syscall`-трап, вообще не линкуя libc.
На Hurd такого пути нет: рантайм вынужден звать функции glibc — то есть
архитектурно ближе к тому, как Go устроен на Solaris/illumos/AIX (там тоже
нет стабильной плоской syscall-ABI и Go линкует libc через cgo-подобный слой)
или на Windows (вызовы через системные DLL), а не как на Linux/*BSD.
**Прецедент есть** (Solaris/illumos/AIX-порты Go существуют и работают), но
это существенно больше работы, чем обычный "ещё один Unix-порт": нужен полный
слой сисколл-обёрток над glibc (аналог `syscall_solaris.go` +
`sys_solaris_amd64.s`), плюс `x/sys/unix`-биндинги под Hurd-заголовки, плюс
netpoller (на Hurd нет `epoll`/`kqueue` — нужен poll()-based или
кастомный).

**3. Linux-бинарной совместимости для Hurd не существует и не строится.**
Официальный FAQ проекта Hurd прямо говорит: потребовался бы userspace-сервер,
перехватывающий Linux-сисколлы и транслирующий их в Hurd-вызовы, "но такого
не существует, и это может быть тяжело реализовать", а "усилия не выглядят
явно оправданными, когда ПО можно просто пересобрать"
(`gnu.org/software/hurd/faq/binary_compatibility.html`). Обсуждалось в
рассылке ещё в 2000-м — и не было реализовано за 25 лет. Для сравнения, у
FreeBSD Linuxulator реален и давно поддерживается, у Hurd — нет даже
прототипа. Учитывая находку про `EINTR`, транслятору пришлось бы
самостоятельно эмулировать прерывание блокирующих syscall'ов сигналом
(например, через `hurd_thread_cancel` над низкоуровневым RPC) для каждого
класса блокирующих вызовов — Hurd это делает не из коробки.

**4. Нет `clone()` с флагами.** Создание потоков на Hurd — это
`task_create`+`thread_create` (Mach) с `pthread_create` поверх них в glibc, а
не единый параметризуемый сисколл как на Linux. Это одинаково влияет на (а) и
(б) — обоим вариантам создание ОС-потоков придётся делать либо через
`pthread_create`, либо вручную собирать Mach-примитивы; принципиальной
разницы в сложности между (а) и (б) здесь нет.

### Пересмотренная оценка

До сегодняшних PoC главным неизвестным риском для (а) считались futex и
сигналы — оба сняты: **все три примитива, от которых зависит рантайм Go
(futex-аналог, доставка сигналов, sigaltstack+si_addr), подтверждённо
работают**. Единственная найденная проблема (`EINTR`) практически не задевает
модель preemption в Go (та работает через переписывание PC в обработчике для
"живых" горутин, а не через прерывание syscall'а).

При этом независимое исследование показало, что:
- у (а) есть реальная, но *ограниченная и прецедентная* архитектурная плата
  — переход на syscall-модель "через glibc", как у Solaris/AIX/Windows-портов
  Go, плюс написание netpoller'а с нуля;
- у (б) прецедента нет вообще, сам проект Hurd оценивал эту идею и отклонил
  её как "тяжело и не факт что стоит того", а объём работы принципиально
  больше: не ограниченный набор из ~15-20 примитивов рантайма (как нужно для
  Go), а *весь* Linux ABI (сисколлы, `clone`-флаги, `ioctl`/`procfs`/`netlink`,
  mmap-семантика, плюс теперь ещё и собственноручная эмуляция `EINTR`) — это
  открытый, никогда не завершающийся объём работы, что на практике
  демонстрируют долгожители вроде FreeBSD Linuxulator (десятилетия
  поддержки) и история WSL1 (в итоге заменили на настоящее ядро Linux в
  WSL2, потому что уровень трансляции syscall'ов не тянул совместимость).

**Вывод:** (а) нативный порт Go остаётся заметно менее трудозатратным, чем
(б) Linux-транслятор, и разрыв не сократился, а увеличился по итогам сегодняшних
находок — риски (а) снялись (futex/signal/sigaltstack работают), а по (б)
всплыл дополнительный неучтённый пункт работы (эмуляция `EINTR`) поверх и без
того неограниченного объёма задачи трансляции целого ABI, который сам проект
Hurd признаёт нецелесообразным. Если цель — "запускать программы на Go на
Hurd", вариант (а) обещает более узкий и предсказуемый фронт работ; вариант
(б) даёт более общий результат (любой Linux-бинарник), но ценой открытого и
исторически не решённого объёма инженерных работ.

## Фаза 1 порта Go (unxed/go, ветка `golang-1.26-hurd`): hello world работает

Выбран вариант (а) — нативный порт рантайма Go (см. выше). Итог первой вехи:
программа `func main() { println("hello from hurd") }`, кросс-скомпилированная на
Linux (`GOOS=hurd GOARCH=amd64 CGO_ENABLED=1`, workflow `hurd-cross-build` в
`unxed/go`), **реально запускается на GNU Hurd в QEMU и завершается с кодом 0**
(`poc/hurdhello.bin` здесь — эталонный бинарник; запускается тем же
`run-hurd-poc.yml`).

Что понадобилось, кроме собственно файлов порта (подробности и причины — в
`unxed/go/STATUS-HURD.md`):

- все константы/раскладки структур сняты с реального Hurd пробником `poc/abi_probe.c`
  (errno — это Mach-коды `0x40000000+`, номера сигналов >15 не как в Linux,
  `pthread_attr_t` = 48 байт, `gregs[23]` как у glibc, …);
- `pthread_create`/`sem_*` лежат в отдельной `libpthread.so.0.3`;
- четыре бага при запуске, найденные и исправленные по реальным прогонам:
  пропущенный `hurd` в TLS-самопроверке `rt0_go`; динамические импорты
  (`R_X86_64_GLOB_DAT`) нужно разыменовывать перед вызовом; точка входа ELF
  получает `argc/argv` на стеке (как Linux), а не в регистрах (как у Haiku).

Ещё не сделано: `syscall`/`os`/`net` (пока только `runtime`), `stat`, нативный
`gsync`-lock, `go test` рантайма.

## Фаза 2 порта Go: `fmt`, `os`, файлы, pipe, горутины работают на Hurd

Порт `syscall`, `internal/syscall/unix`, `internal/poll`, `os` (`unxed/go`, ветка `golang-1.26-hurd`).
Программы `t_os`, `t_fmt`, `t_fs`, `t_rt` (`poc/gotests/*.bin`, собраны кросс-компиляцией в CI) запускаются на
Hurd в QEMU и завершаются с кодом 0 (run-hurd-poc #35380952163): `fmt.Println/Printf`, `os.Stat/ReadFile/
WriteFile/ReadDir/Remove/Pipe/Getwd/Hostname`, горутины, `time.Sleep`, тикеры, GC.

Константы и раскладки структур сняты с реального Hurd генератором `poc/mkhurd.sh` + `poc/mkztypes_hurd.c`
(запускается в госте; `run-hurd-poc.yml` с входом `mkhurd=true`, результат — артефакт `hurd-generated`).
Ключевые находки: errno — Mach-коды `0x4000xxxx` (а `EKERN_*`/`EMIG_*` из `<errno.h>` — не errno);
`getdirentries()` → `ENOSYS` (каталоги читаются через `fdopendir`/`readdir_r`); `struct stat` = 192 байта;
`sockaddr` с `sa_len`; `UTIME_OMIT=-2`; `d_type` на ext2fs всегда `DT_UNKNOWN`. Подробности — `STATUS-HURD.md`
в `unxed/go`.
